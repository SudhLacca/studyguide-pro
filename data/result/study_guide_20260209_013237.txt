KEY CONCEPTS & DEFINITIONS
--------------------------------------------------------------------------------
Software Testing Life Cycle (STLC): A series of activities that ensure the software is thoroughly tested and validated before its release. Test Planning: The process of defining the overall testing strategy, scope, objectives, resources, tools, and environments. Static Testing: A type of testing that involves evaluating software without executing the code. Dynamic Testing: A type of testing that involves executing the software to identify defects. Black-box testing: A type of testing where the tester is not concerned with the internal knowledge or implementation details of the software. White-box testing: A type of testing that involves analyzing the internal structures, data structures, internal design, code structure, and the working of the software. Integration testing: A method of testing how different units or components of a software application interact with each other. Top-down integration testing: A method of integration testing that starts with the highest-level modules and differentiates them from lower-level modules. Bottom-up integration testing: A method of integration testing that starts with the lowest-level modules and integrates them with higher-level modules. Big Bang approach: A method of integration testing where all modules are integrated at once. Equivalence Partitioning: A black-box test technique used to reduce the number of required test cases by identifying classes of inputs with the same behavior. Decision Tables: A technique used to identify and test the possible combinations of inputs and their corresponding outputs. Error: A human mistake in coding or design. Defect: A flaw in the software due to an error. Failure: A deviation of software from its expected behavior during execution. Beta Testing: A type of testing performed by real users in a real-world environment before the final launch. Alpha Testing: A type of testing performed at the developer's site, in a controlled environment, before the software is released to external users.

COMMON MISTAKES TO AVOID
--------------------------------------------------------------------------------
MISTAKE: Static testing is the same as dynamic testing. CORRECT: Static testing is the process of evaluating software without executing the code, whereas dynamic testing involves executing the code to test its functionality. MISTAKE: Integration testing is only done at the end of the software development life cycle. CORRECT: Integration testing is typically done after unit testing and before functional testing to ensure that different units of the software work together as intended. MISTAKE: Beta testing is performed by developers in a controlled environment. CORRECT: Beta testing is performed by real users in a real-world environment to collect user feedback and detect real-world issues. MISTAKE: Equivalence partitioning involves testing all possible values of input. CORRECT: Equivalence partitioning involves identifying classes of inputs with the same behavior and testing at least one member of each equivalence class. MISTAKE: Big Bang integration testing is the most efficient approach. CORRECT: While Big Bang integration testing may be simple and time-saving initially, it poses a high risk of failure and is not suitable for complex systems. MISTAKE: Alpha testing is done after beta testing. CORRECT: Alpha testing is typically done before beta testing to identify and fix major issues in the software. MISTAKE: Static testing is only done by the writer or developer of the software. CORRECT: Static testing can be done by anyone, including testers, who review documents, design, or source code to detect defects early.

PRACTICE QUESTIONS
--------------------------------------------------------------------------------
Q: What is the main goal of test planning in the software testing life cycle? A: The main goal of test planning is to define the overall testing strategy by deciding on the scope, objectives, resources, selecting tools and environments, estimating effort and schedule, and identifying risks and mitigation. Q: What is the purpose of static testing techniques? A: The purpose of static testing techniques is to detect defects early by reviewing documents, design, or source code, and to improve quality, detect errors early, and ensure compliance with standards. Q: What is the difference between alpha and beta testing? A: Alpha testing is performed at the developer's site in a controlled environment, while beta testing is performed by real users in a real-world environment. Q: What is the main advantage of black-box testing? A: The main advantage of black-box testing is that the tester does not need to have in-depth knowledge of the internal workings of the software, making it efficient and easy to implement. Q: What is equivalence partitioning? A: Equivalence partitioning is a black-box test technique that reduces the number of required test cases by identifying classes of inputs with the same behavior and testing on at least one member of each equivalence class. Q: What is the purpose of integration testing? A: The purpose of integration testing is to identify and resolve issues that may arise when different units of the software are combined, ensuring that the different units of the software work together as intended. Q: What is the main disadvantage of big-bang integration testing? A: The main disadvantage of big-bang integration testing is that it is high-risk, as major system failures may be detected late, and it can be difficult to pinpoint the root cause of the failure. Q: What is the main goal of test case development? A: The main goal of test case development is to design tests that validate requirements by writing test cases and scenarios, preparing test data, and reviewing and baselining test cases. Q: What is the difference between static and dynamic testing? A: Static testing is carried out before putting the software in action, while dynamic testing is carried out once the software has been fully compiled and loaded to the system. Q: What is the purpose of decision tables? A: The purpose of decision tables is to create a table that lists all possible conditions and their corresponding actions, making it easier to test complex software requirements.
